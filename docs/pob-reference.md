# Bounded PoE1 Spark reference comparison

The supported fixture suite compares **selected-skill hit DPS and CombinedDPS** for normal Spark, part 1 (`1 Hit`). It counts one lightning hit per self-cast; hits per second equal casts per second. Disabled critical mode uses the noncritical mean. Explicit average-critical mode mixes noncritical and critical means by critical chance. CombinedDPS equals hit DPS because this slice excludes ailments, damage over time and other damage sources. Projectiles, duration, return paths, repeat collisions and the skill group's Full DPS count do not multiply this metric.

This is an **executed comparison with a pinned PoB development oracle**. A separate PoB checkout and its LuaJIT runtime ran the unmodified official headless wrapper outside this repository. Only versioned JSON results entered Exile Engine. The same XML fixture bytes passed through PoB's XML/item/skill/config loaders and through the adapter. The independent JavaScript arithmetic in `tests/pob-reference.test.mjs` additionally follows the reviewed branches below. All thirty-six supported fixtures pass within the stated tolerance; this establishes this fixture set, without claiming complete PoB parity.

## Versions and source authority

The reference is [Path of Building Community commit `3dbca4463c0a59079d9f7f032d8240cf868e09da`](https://github.com/PathOfBuildingCommunity/PathOfBuilding/tree/3dbca4463c0a59079d9f7f032d8240cf868e09da). Engine rules identify themselves as `poe1-selected-spark-v5`, implemented as changes on repository base `88cab58d97dac8c75ca16b748da5c81fef2e5eb7`. The worktree changes are part of the result, rather than a claim that the base commit already contained them. `tests/fixtures/pob-reference.json` records both revisions, SHA-256 fingerprints of the changed calculation/adapter sources and XML fixtures, reference Git blob IDs, runtime identity, the exact game/build/snapshot identity, assumptions and numeric tolerance. `tests/fixtures/pob-oracle-output.json` retains the observed PoB output and modifier breakdown.

The engine loads the committed PoE1 client snapshot for build `26474023`, snapshot `cfbf5330f9d85f67070aa163bfd7b1e5d1eb6dc4a045bccfd408708963b052c2`. The independent pinned-source coefficient calculation resolves level 20 Spark to the same 104–1983 base lightning damage. The pinned reference and the installed game build are separate identities: matching this skill's records does not establish that all their data is identical. The engine's base damage authority remains the client snapshot.

Added damage effectiveness also comes from that client snapshot. `GrantedEffectStatSetsPerLevel.DamageEffectiveness` is 9000 in the checked Spark rows, normalized as `1 + raw / 10000 = 1.9`. It is a multiplier, so 10–20 added lightning supplies 19–38 effective added lightning. The record identifies the exact table keys and row indices at levels 1, 20 and 40; tests compare the normalized dataset values to those source fields. The pinned PoB export and executed skill both independently give 1.9. The normalizer fails on missing or invalid facts, rather than inferring effectiveness from a skill name or substituting 1.

Controlled Destruction is the only supported support gem: normal variant, gem levels 1–20, quality 0. Client `GrantedEffects:5539` joins statset 5547 and the exact damage/critical stat IDs. Its per-level spell-damage modifier is 25% more at level 1 and 39% more at level 20; all twenty values are checked against client rows. Its constant critical chance modifier is 80% less, and its source cost multiplier is 140%. Eligibility is checked against normal Spark's actual `Damage` skill type. No caller-provided multiplier or expression supplies these rules.

Spark's base critical chance comes from the same client level row: `SpellCritChance = 600`, divided by 100 to give 6%. The base player critical multiplier is a distinct pinned rule, 150%, sourced from PoB `Data/Misc.lua:89` and its use in `CalcSetup.lua:615`. It is explicitly identified as an external rule source; no client `GameConstants` row is invented for it. The three supported critical modifier IDs resolve against exact snapshot `Stats` rows 556, 558 and 95.

Resistance inputs also keep exact client vocabulary. Penetration resolves `base_reduce_enemy_lightning_resistance_%` from snapshot `Stats:597`; exposure resolves `lightning_exposure_on_hit_magnitude` from `Stats:16084`. Exposure magnitudes are authored as negative values: the verified `Mods:28533` row `LightningExposureEffectOnHitEldritchImplicit1` contains -11 for that exact stat. The 75% default maximum, 90% hard maximum and -200% resistance floor are separate pinned PoB rule constants with an external source identity; the engine does not invent client rows for those constants.

## Fixtures and assumptions

`tests/fixtures/pob/` contains synthetic plain XML with explicit Build `targetVersion="3_0"`. Each successful fixture selects one enabled normal Spark gem at level 20, or level 1 for the named low-level case, quality 0, part 1, with no passives or other active skills. The named support fixtures add one normal Controlled Destruction gem to the same selected socket group. Equipped item text contains only explicitly supported damage, cast-speed and critical lines and spell-specific flat added lightning ranges, and no implicit modifiers. The enemy is explicitly `None` for boss selection and has the listed lightning resistance. The original sixteen noncritical fixtures use literal `Never deal Critical Strikes`; the ten `crit-` fixtures use literal `Cannot inflict Elemental Ailments`, which selects explicit average-critical mode with excluded ailments. Nine new resistance fixtures use the noncritical assumption, and `lightning-resistance-combined` uses average critical mode. Exposure and penetration apply only in the named resistance fixtures. There is no shock, lucky damage, conversion, other added damage type, triggered casting, repeats, or damage over time. Chance to hit is 100%; skill DPS multiplier and quantity multiplier are both 1. No mana-sustain assertion is made. The executed oracle caught the need for `targetVersion`: omission invokes PoB's legacy conversion path, so the adapter now rejects it.

The only added-damage item grammar is `Adds X to Y Lightning Damage to Spells`, with safe nonnegative integer endpoints and `X <= Y`. Each authored line retains the ordered pair `spell_minimum_added_lightning_damage`, `spell_maximum_added_lightning_damage`, its two values and item/line provenance. Multiple lines remain distinct contributions. Generic, local weapon and attack-only added damage, other elements, conditions and ambiguous range interpretations remain unsupported. Individual endpoints supplied as unrelated percentage modifiers are rejected.

Chance is `clamp(round(baseChance × (1 + increasedChance / 100) × lessChance × 100) / 100, 0, 100)`, in percentage points. There is no 5% minimum: the active support fixture reaches 1.2%. The rounded case preserves 1.404% until rounding to 1.40%. The controlled-cap fixture distinguishes applying less chance before the cap: 126% × 0.2 gives 25.2%, whereas capping first would incorrectly give 20%.

The critical multiplier is `1 + max(0, (baseMultiplierPercent - 100 + addedMultiplierPercent) / 100)`, with a minimum of 1. The API also tests negative multiplier additions and that floor. Critical hit endpoints are the already-rounded noncritical endpoints multiplied by that factor, without another rounding stage. For example, baseline critical damage is 156–2974.5 before resistance. Resistance scales each critical endpoint and its mean. Expected damage is `noncriticalMean × (1 - chance/100) + criticalMean × chance/100`; multiply this mean by the same casts per second for hit/combined DPS. Critical chance does not add casts or hits.

`criticalEffects` retains base chance, additive totals, support less chance, unrounded/rounded/capped chance, base/added multiplier, critical ranges before/after resistance, expected means, source rows and individual item contributions. `hit` remains the noncritical trace. Absent critical mode retains the earlier disabled behavior; average mode requires explicit excluded ailments. Disabled mode keeps nominal source facts visible while applying zero critical probability. The base player multiplier's external provenance remains explicit in both modes.

Every XML fixture now supplies a raw-resistance profile. The original twenty-six XML files are byte-for-byte unchanged and retain the same DPS: their 0% or 25% raw resistance needs no clamping, exposure or penetration. The API's earlier `effectiveLightningResistancePercent` profile remains available for explicitly already-effective values, with its original range. It cannot be combined with raw resistance, exposure or penetration; the adapter uses the raw profile and makes the distinction explicit.

The new profile accepts integer base resistance from -1000% through 1000%, up to eight explicit exposure states with integer magnitudes from -100% through 0%, and integer penetration contributions from 0 through 200 percentage points with a total no greater than 200. These are bounds of this implemented slice. Penetration item text is exactly `Damage Penetrates N% Lightning Resistance`. Each exposure retains its own scenario source, enabled state and canonical stat ID. Enabled exposures do not add: select the strongest negative magnitude once. Equal strongest sources remain visible in the engine trace.

The resistance stages are:

1. Select the strongest enabled exposure and add it to raw base resistance.
2. Resolve the maximum from the original raw resistance. PoB's `enemyMaxResist=true` checkbox means the default 75% maximum. False or absent means `min(max(rawResistance, 75), 90)`; this profile does not accept an arbitrary numeric maximum.
3. Clamp the exposed resistance to that maximum and the -200% floor.
4. Subtract total penetration. There is no second floor after penetration.
5. Apply `1 - effectiveResistance / 100` to both noncritical and critical damage. Probability weighting and cast/hit counts stay the same.

The overcap pair distinguishes exposure before the cap from penetration after it: 110 - 15 gives 95, then the 90% cap and 20 penetration give 70%; the default-maximum checkbox instead gives 55%. The floor case clamps -220% to -200% before subtracting 20 penetration, giving effective -220% and a 3.2 damage factor. The combined fixture includes added lightning, 100% increased damage, 25% cast speed, Controlled Destruction and expected critical damage. Its noncritical mean after resistance is 894, its critical mean is 1788, and 3% critical chance gives an expected mean of 920.82 and DPS 1918.375.

Exposure is an explicitly active state in this snapshot calculation. `enabled` does not simulate a chance to apply exposure, the first hit, duration or uptime, and damage does not feed back into exposure state. The PoB oracle expresses this selected state using the literal `Inflict Lightning Exposure on Hit, applying -N% to Lightning Resistance`; its Effective calculation supplies the active exposure. This adapter accepts that exact line only in up to eight uniquely titled custom modifier blocks, with each nonempty title bounded to 128 characters. The fixtures name them `Exposure 1` and `Exposure 2` to preserve distinct source identities. The separate enabled block `Exile Engine Assumptions` holds exactly the critical/ailment assumption. Disabled exposure blocks retain their authored source and value while contributing no reduction. Mixed legacy `Input customMods` plus blocks is rejected: the executed oracle showed that PoB drops the legacy literal when explicit blocks exist. Unknown block text remains unsupported even when disabled.

`resistanceEffects` reports the profile, raw value, maximum mode, both caps, all exposure states, selected exposure indices, uncapped/capped resistance, all penetration contributions, final effective resistance, damage factor and source identities. The native PoB evidence independently records raw configuration, exposure candidates, the selected enemy resistance contribution, penetration item contributions and the final lightning damage multiplier. Curses, exposure boosts/overrides, elemental equilibrium, resistance inversion or ignoring resistance on critical hits remain unsupported.

The no-damage case has a supported mathematical zero, unlike missing or unsupported data. A zero added pair is also explicit supported input and keeps its provenance. `missing-config`, `unsupported` and `added-lightning-reversed` must retain diagnostics/unresolved data and expose no selected-skill input, so they cannot be mistaken for zero-DPS successful imports.

Every numeric comparison uses `abs(actual - expected) <= 1e-9 + 1e-12 * abs(expected)`. The tests check intrinsic base endpoints and mean, each exact stat ID/value and item-line source identity, raw added groups and totals, effectiveness, fractional effective added/combined-base ranges, additive totals, pre/post-resistance endpoints and mean, cast time, cast frequency, hit count, included damage, hit DPS and CombinedDPS. The PoB breakdown records pre-resistance integer endpoints separately from fractional effective endpoints. Explicit comparison-only mappings translate observed PoB `Damage` flags 0/2/1024, `LightningDamage` flag 0 and `Speed` flag 16 to the five increased-stat IDs. `LightningMin`/`LightningMax` with flags 0 and spell keyword 131072 map to the two exact added game stat IDs; every source is the equipped synthetic item. PoB's applicable `Tabulate` output omits zero values, so its original parsed item lines also verify ordered groups and the zero pair. Saved PoB output fields do not provide the engine's answer: the fixtures deliberately contain a false cached CombinedDPS of 999999999, which both live calculators replace.

For every supported XML fixture, a new incremental session and its unchanged-input update must deeply equal the fresh full result, including grouped provenance, support/critical contributions and all intermediate ranges. Critical comparisons check all chance stages, multiplier totals, critical hit mean, probability-weighted hit mean, actual item contributions, explicit ailment flags and the retained player base source. Resistance comparisons check raw/uncapped/capped/effective values, maximum mode, strongest and disabled exposure sources, summed penetration sources and the common critical/noncritical factor. Support comparisons check raw more/less stats, source rows, eligibility, enable state, cost factor, unchanged cast timing and actual PoB `MORE` contributions. Separate mutation tests exercise changes to added endpoints, group membership, support level/enable state/source identity, critical modifiers, critical mode, increases, skill level, penetration, exposure source/strength/enable state, maximum mode and enemy configuration; see the incremental/performance documentation for recalculated nodes and batch measurements.

## Scope limits and next comparisons

The suite is deliberately small. Executed headless parity covers these thirty-six supported synthetic fixtures and their stated assumptions. GUI behavior, arbitrary builds, tree allocation, other items, other support gems, support quality effects, conditional mechanics, lucky/special critical rules, ailments and other skills remain outside the evidence. Missing/unsupported fixtures test the adapter's refusal behavior, without requiring PoB to reject mechanics it implements. The isolated-hit API's supported modifier vocabulary is unchanged; added-damage, support, critical and resistance-pipeline behavior belong to the PoE1 selected-skill API.

Prioritize a separately configured ailment such as shock next, with an explicit state and damage-taken rule. Conditional applicability should follow with a specified state model and feedback behavior. A support that changes casting cadence needs its own rule and fixtures; Controlled Destruction's unchanged factor does not implement repeats, triggers or other supports. See `docs/roadmap.md`. Spark multi-hit collision estimates and Full DPS remain separate future metrics; this result does not justify automatically adding other skills.
