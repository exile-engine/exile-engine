# Roadmap

## Implemented foundation

- Seven portable ESM package boundaries and strict TypeScript builds.
- Source-only repository/package checks and isolated package-consumer validation.
- Versioned client build catalogs, source provenance, SD locales, item templates and passive topology.
- Normal Spark noncritical single-hit calculation and tested English/Thai item-text interpretation.
- Bounded synthetic PoE1 PoB XML adaptation and deterministic normal Spark selected-skill calculation.
- Fresh recomputation, dependency-tracked sessions, dynamic applicability invalidation and explicit feedback rejection.
- Ordered spell added-lightning ranges with client-derived effectiveness, intermediate provenance, executed pinned PoB fixtures and selective invalidation.
- One normal Controlled Destruction support with explicit more/less/cast-time rules, gem and source-row provenance, executed oracle fixtures and selective support invalidation.
- Explicit average critical hits with client base chance, a pinned player multiplier rule, Controlled Destruction less crit, excluded ailments, exact scalar modifier provenance and fresh/incremental oracle checks.
- Explicit already-active lightning exposure, reviewed maximum/floor profiles and post-cap penetration, with staged provenance, pinned oracle fixtures and selective resistance invalidation.
- Explicit enemy shock magnitude and host uptime, separate shocked/unshocked traces, scenario provenance, executed pinned endpoints and full/incremental checks.
- Normal Faster Casting as a second support, additive item/support cast speed, explicit cast-time and tick rules, independent Controlled Destruction interaction and per-gem provenance.
- One already-active normal Conductivity, explicit curse effect with negative truncation, pre-cap resistance ordering, excluded side-stat provenance and pinned/full/incremental comparisons.

## Next capabilities

1. Add one conditional modifier against explicit enemy state with changed-applicability tests. Distinguish active zero-effect curses from absent/disabled curses; an applied resistance delta alone does not establish curse presence.
2. Review additional damage-taken modifiers separately before combining their additive pool with shock. Further curse/hexproof/boss-effect rules need distinct configured profiles and pinned comparisons; no application or uptime is inferred from this curse slice.
3. Expand item reconciliation and passive/equipment integration within normal Spark. Generated shock needs a threshold/application/duration model; supports that add repeats or triggers need explicit timing/hit-count rules. Feedback mechanics require bounded solver semantics.
4. Evaluate graph overhead and data validation costs using representative workloads before extending incremental machinery. Add further skills/variants only as separate documented, tested slices.

No future item is exposed as a successful runtime API before it works. Publishing remains a separate manual release decision; no npm publishing credentials or trusted publishers are configured by the scaffold.
